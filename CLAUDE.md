# Scale Shift: notes for Claude Code

Real-size world map with 4,000 years of borders (2000 BCE to today), a daily "which is bigger?" game with a public leaderboard, and history pages. Next.js 16 (App Router, Cache Components on), TypeScript, Tailwind 4, d3-geo on canvas. No map tiles or API keys.

**Read `docs/PROJECT.md` at the start of any new task.** It has the goal, decisions, design system, quality bar and roadmap.

## Team: shared ownership
Anthony (Mac) and Evan (Windows) both own the whole project with equal rights. Either can change any file, merge and ship it, including UI, map engine, data and dependency changes. Neither ever needs the other's approval: once CI passes, merge it. Each owner's Claude notifies its owner when the other ships something.

## "Ship it" means
1. `git switch main && git pull`
2. `git switch -c <short-branch-name>` (e.g. `add-aztec-comparison`)
3. Make the change.
4. `npm run lint && npm run typecheck && npm run build && npm run check:data` must all pass (CI runs the same). Fix failures; never skip checks.
5. Commit with a clear message, then `git push -u origin <branch>`.
6. `gh pr create` with a short summary: what changed, why, and how to see it.
7. `gh pr checks --watch` until CI passes. If it fails, fix it and push again.
8. `gh pr merge --squash --delete-branch`
9. `git switch main && git pull`

If the user says "open it but don't merge", stop after step 7 and give them the PR link.

**Big changes** (layout or visual design, the map engine in `src/lib/geo.ts` or `src/components/map/engine.ts`, the data pipeline, dependencies, anything that deletes features): ship them the same way, no approval needed. Just say what changed and how to see it in the PR, test extra carefully (desktop and phone), and run `scripts/qa/site-check.mjs` against production after the deploy.

**Unattended scheduled runs** (no owner in the conversation) are the one exception: they merge small fixes themselves, but open big changes as a PR and leave the merge to Anthony or Evan.

## Avoid collisions
- Before starting, run `gh issue list` and `gh pr list`. If someone else is already working in the same files, warn the user before editing.
- Suggest opening a GitHub issue for any task bigger than a few minutes and assigning it to whoever is doing it.
- Never push directly to `main`. Never force-push. Never rewrite shared history.
- **Hands off the other owner's work.** Never push to, rebase, merge, close, comment on behalf of, or "fix" the other owner's branches or open PRs, even if CI fails or they're stale. Leave their files alone while their PR is open: if your change would touch the same files, tell your owner and wait for their PR to merge (then merge `main` into your branch). Only exception: the other owner explicitly asks you, in a GitHub comment, to change their PR.
- On a merge conflict: merge `main` into the branch, resolve it keeping both people's intent, rerun the checks.

## Read first (technical)
- This is Next.js 16. APIs differ from older versions: check `node_modules/next/dist/docs/` before using a Next API you're unsure of.
- `params` is a Promise. With Cache Components, reading `new Date()` or `Math.random()` while a page renders fails the build: do it in an effect or event handler.
- React won't run a `<script>` it renders in the browser. Inline scripts belong in the root layout (`src/app/layout.tsx`), which only renders on the server.

## Where things live
- `src/app/(site)/`: content pages with header and footer (home `/`, `/daily`, `/leaderboard`, `/eras`, `/timeline`, `/disputes`, `/about`, `/how-it-works`, `/contact`, `/privacy`).
- `src/app/map/`: the interactive map, its own full-screen page. The homepage never shows the map; it leads to the games, the map and the information pages.
- `src/content/*`: all copy. Change words here, not in components (`site.ts` holds the site name).
- `src/components/map/engine.ts`: canvas map engine (drawing, drag, edge-scrolling). `src/lib/geo.ts`: real-size math. Shapes are rotated on the sphere, never shifted in flat pixels.
- `src/lib/daily.ts` + `scripts/build-daily.mjs`: daily challenge. `src/lib/leaderboard.ts` + `src/app/api/leaderboard/`: leaderboard (scores are re-marked on the server).
- `public/data/`: generated by `npm run data` (downloads sources into `.cache/`). Don't hand-edit. Name and ruler fixes go in `src/content/data-corrections.json`.
- `src/app/api/feedback/`: form endpoint (local JSON file, webhook or Resend email).
- `docs/PROJECT.md`: project brief, decisions, setup status and roadmap. Update it when a decision changes.

## Commands
- `npm run dev`: local site at http://localhost:3000
- `npm run lint && npm run typecheck && npm run build && npm run check:data`: must all pass before a PR
- `npm run data`: rebuild map data, Antarctic claims and the daily puzzle pool
- `npm run leads`: print form submissions saved locally

## Rules
- Map snapshots are keyed `2000bce` … `1914` … `present`. Years before 1 CE are negative in code.
- Historical data is GPL-3.0 (historical-basemaps). Keep the credits in the footer, on /about and in `public/data/LICENSE.txt`.
- Antarctica is drawn with its territorial claims (`src/content/antarctic-claims.json`), each shown only from the year it was made.
- Never commit secrets. `.env*` files are ignored; keys go in Vercel's environment variables.
- Original work only: thetruesize.com inspired the idea, but never copy its text, name, design or code.
